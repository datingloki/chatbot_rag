## Контекст

Бот первой линии отвечает по базе знаний 1С:Полиграфии (FAQ, руководство, архив OmniDesk — 4 305 фрагментов): уточняет неполный вопрос, отвечает со ссылкой на источник или предлагает консультанта. Контракт требует выполнять правила гарантированно: ответ только по найденным фрагментам (C03), не больше 5 уточнений на проблему (C04), отказ вне домена (C05), передача только после согласия (C06), никаких советов править базу (C07), честное сообщение о сбое (C09). Бюджеты: полный ответ P95 ≤ 15 с; один вызов модели стоит 0,33–0,54 ₽, ход с ответом занимает 1,9–4,3 с, поиск — P95 1,7 с (замеры 18.11.2026). Вопросы одношаговые («как сделать X в программе»), внешнее действие у бота одно — передача консультанту. Бейзлайн S0 на dev уточняет 0 из 49 неясных вопросов и оставляет оператору 213 из 275 доменных (78%) — даже на кейсах, на которых построены его интенты.

## Решение

Выбрали **A — фиксированный граф из 14 узлов с одним вызовом LLM на сообщение** (`bot/polybot/graph_config.py`, без фреймворка). Решающими были два обстоятельства. Первое — контракт: пять обязательств (C03–C07) выполняются кодом, а не просьбой к модели, и это проверяется сценариями без модели (9 из 9 в режиме `scripted`). Второе — бюджет: один вызов модели держит ход в 1,9–4,3 с и ≤ 0,54 ₽, а агентный цикл в 2–5 вызовов приблизил бы хвост задержки к 15 с и сделал бы стоимость хода непредсказуемой. Задачи при этом одношаговые: повторный поиск и планирование не дают выигрыша, который бы это окупил. Фреймворк (C) не нужен: граф маленький и без циклов, а своя обвязка с проверкой графа, бюджетом шагов (10 узлов, самый длинный путь — 7) и записью шагов под span'ы Langfuse короче адаптации.

## Последствия

- Плюсы: поведение предсказуемо — у каждого хода известен путь и причина ответа, видимые в трассе без финального текста. Стоимость хода ограничена одним вызовом модели. Правила контракта гарантирует код, проверка домена в промпте — второй рубеж. Граф проверяется при сборке (у каждого решения узла есть переход, каждый узел доходит до `final`), его схема в README сверяется с кодом тестом.
- Минусы: один поиск на ход — модель не может сама переформулировать неудачный запрос, вместо этого бот уточняет у пользователя (до 5 раз) или предлагает консультанта. Новое действие (например, отправка в OmniDesk) добавляется узлом или действием `Bot`, а не «появляется» у модели. Граф и узлы поддерживаем сами.
- Что нужно сделать из-за этого решения: держать сценарии S1–S9 и тесты графа зелёными при каждом изменении; прогнать RAG на dev против S0 (M17 без регрессии M03, M06, M10) и полные диалоги K5/K6 (D1–D4, design doc 7.3); замерить P95 полного ответа на наборе.
- При каких условиях пересматриваем:
  - D1 на K5 (полные диалоги) окажется низким из-за неудачного первого поиска — добавляем узел переформулировки запроса моделью: это всё ещё фиксированный граф, но с двумя вызовами LLM;
  - типичный вопрос станет многошаговым: например, нужно будет запросить данные базы клиента через API, найти инструкцию под её релиз и проверить результат — тогда рассматриваем агентный цикл B, если модель на сценариях S3, S4, S7–S9 соблюдает правила без проверок в коде, а бюджет допускает 3–5 вызовов на ход;
  - граф вырастет до 25–30 узлов с циклами и параллельными ветками — рассматриваем фреймворк C;
  - база знаний сократится до десятков статей и целиком поместится в окно модели в пределах бюджета 3.3 — рассматриваем D.

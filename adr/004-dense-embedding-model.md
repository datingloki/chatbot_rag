## Контекст

Поиск — гибрид dense + BM25 + BM25 по заголовкам с взвешенным RRF (4.3). Dense-часть слабая: в режиме «только dense» руководство находится в 36 из 125 кейсов dev, а BM25 — в 83; поэтому BM25 получил вес 2. Текущая модель `paraphrase-multilingual-MiniLM-L12-v2` обучена на входе до 128 токенов: у 72 % из 4 305 фрагментов текст длиннее (медиана — 178 токенов), и вектор видит в среднем ≈ 72 % текста (замер 20.11.2026). Ограничения: CPU без GPU (4.6), задержка поиска входит в бюджет хода (P95 15 с, дедлайн 25 с), русский язык.

| Вариант | Качество на dev (гибрид, hit@5) | Задержка и ресурсы | Статус |
|---|---|---|---|

| B. **MiniLM, лимит 256 токенов** | Хуже: руководство 101 → 95, hit@1 57 → 42; FAQ дословно 38 → 37; «только dense» — руководство 36 → 31 | Сборка 537 с | Отклонён 20.11.2026 (8.2, строка 5) |

## Результаты эксперимента с C (22.11.2026)

Dev, `python -m harness.retrieval_eval`; для e5 — лучшая гибридная конфигурация (веса RRF: dense 1, BM25 1, заголовки 1), для MiniLM — рабочая (BM25 = 2).

| Метрика | A. MiniLM | C. e5-large | Изменение |
|---|---|---|---|
| Руководство, «только dense», hit@5 | 36/125 (29 %) | 92/125 (74 %) | +56 кейсов (+45 п. п.) |
| Руководство, гибрид, hit@5 | 101/125 (81 %) | 108/125 (86 %) | +7 кейсов |
| Руководство, гибрид, hit@1 | 57/125 (46 %) | 64/125 (51 %) | +7 кейсов |
| Перефразы FAQ, гибрид, hit@5 | 19/21 (90 %) | 18/21 (86 %) | −1 кейс |
| Эмбеддинг запроса | ≈ 15 мс | ≈ 80 мс | ×5 |
| Сборка индекса | ≈ 4 мин | ≈ 95 мин | ×24 |

**Проверка критериев** (заданы до эксперимента):

| Критерий | Результат |
|---|---|
| Гибрид, руководство hit@5 выше 101/125 | ✅ 108/125 |
| Рост больше шума (1–3 кейса) | ✅ +7 по hit@5 и hit@1 |
| Перефразы FAQ не ниже 19/21 | ❌ 18/21 — в пределах шума, но критерий формально не выполнен |
| FAQ дословно не падает | не измерено в отчёте эксперимента |
| Эмбеддинг запроса до ≈ 0,3 с | ✅ ≈ 80 мс |

**Что подтвердилось.** Гипотеза о слабом dense верна: e5 находит руководство без помощи BM25 в 2,5 раза чаще, чем MiniLM, — ограничение было в модели, а не в нарезке. Под e5 BM25 больше не нужен вес 2.

**Открытые проблемы.**
1. **Прирост гибрида мал относительно прироста dense.** +56 кейсов в «только dense» превратились в +7 в гибриде: BM25 уже находил большую часть того, что теперь находит e5. Веса RRF подобраны только грубо (BM25 = 1).
2. **Перефразы FAQ −1 из 21** — нарушен критерий; надо разобрать этот кейс.
3. **`evidence_gate` не работает с e5.** При текущем `min_score = 0.5` проходят даже запросы, ответа на которые в базе нет: у e5 косинусы смещены вверх, и порог для MiniLM ничего не отсекает. Без нового порога внедрять C нельзя — сломается «нет ответа в базе».
4. **Предупреждение о смене pooling** при загрузке модели — не разобрано. Нужно проверить, что эмбеддинги считаются так, как модель обучалась; иначе результаты C могут быть занижены (или сравнение некорректно).
5. **Ресурсы.** Модель в 10 раз больше (2,24 ГБ против 0,22 ГБ), сборка индекса — ≈ 95 мин вместо ≈ 4 мин: пересборка после обновления источников (4.3) перестаёт быть быстрой операцией.
6. **Задержка полного поиска** на замерах стала ниже, чем у A, несмотря на более медленный эмбеддинг, но замеры несопоставимы; для вывода нужен повторный замер в одинаковых условиях (3.2).

## Решение

Рабочим остаётся **A (MiniLM, 128 токенов)**. C не внедряем на КТ3:
- качество dense выросло сильно, но итоговый гибрид — на 7 кейсов из 125, а цена — ×5 к эмбеддингу запроса, ×24 к сборке индекса и +2 ГБ RAM;
- не выполнен критерий по перефразам FAQ;
- `evidence_gate` для e5 не настроен, а с текущим порогом нарушается сценарий «нет ответа в базе»;
- не разобрано предупреждение о pooling.

Пересматриваем решение на КТ4 после шагов ниже. Внедряем C, если после них критерии выполнены полностью и прирост гибрида не меньше нынешних +7 кейсов.

## Следующие шаги (до КТ4)

1. Разобрать ошибки e5: кейсы руководства, где A права, а C нет, и потерянную перефразу FAQ.
2. Разобраться с предупреждением о pooling; при исправлении — перемерить C.
3. Подобрать веса RRF под e5 (dense выше BM25, вес заголовков) на dev.
4. Подобрать `min_score` для e5 по распределению скоров «есть ответ / нет ответа».
5. Измерить FAQ дословно и повторить замер задержки поиска для A и C в одинаковых условиях.

## Последствия

**Сейчас (A остаётся):** индекс, веса RRF и `min_score` не меняются; поиск по-прежнему опирается на BM25 (вес 2).

**Если на КТ4 выберем C:**
- Пересобрать рабочий индекс (≈ 95 мин на CPU); подобрать порог `evidence_gate` (`min_score`) и веса RRF заново (8.2).
- Учесть 2–3 ГБ RAM на модель на сервере пилота (4.6) и ≈ 80 мс эмбеддинга запроса в 3.2.
- Прогнать dev целиком (M01, M17) — рост hit@5 не гарантирует роста качества ответов.
